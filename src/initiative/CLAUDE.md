# Initiative pipeline detail

Loaded automatically when Claude reads a file under `src/initiative/`. Companion to the root `CLAUDE.md`; read that first for the message flow and cross-cutting settings.

**Initiative** (`src/initiative/`): the bot deciding, unprompted, that a conversation is worth a line — a separate scoring call behind deterministic gates. Ships as a dry run (`INITIATIVE_ENABLED=False`). See **Initiative pipeline** below.

### Initiative pipeline (`src/initiative/`)

An unprompted reply — the bot deciding a conversation it was not addressed in is worth a line. It replaces `RANDOM_REPLY_CHANCE`/`RANDOM_REPLY_COOLDOWN_MINUTES`, which fired on a coin flip with no idea what it was interrupting.

`handlers.py:run_initiative_checks` is the first stage of `run_context_checks`, so it is evaluated after every message. In order:

1. **Kill switch** — `settings.INITIATIVE_CHECKS_ENABLED` off returns before any DB read. It is one of *two* flags: `INITIATIVE_ENABLED` gates only the final send, so the pipeline can run as a dry run — evaluated, scored and logged, nothing sent. That is how it ships (`INITIATIVE_CHECKS_ENABLED=True`, `INITIATIVE_ENABLED=False`), and it is what calibrates the threshold against real conversations.
2. **Claim** (`_claim_window`) — read the watermark, fetch the window, run `pre_check`, advance the watermark, all inside `INITIATIVE_RUN_LOCK`. The lock is module-level and shared by every chat, like `CHAT_CONTEXT_LOCK`, but the critical section ends *before* the LLM call. It is what makes the read-then-write atomic: `run_context_checks` is a detached task per message, so two messages arriving together would otherwise both read the same watermark, claim the same window and answer it twice.
3. **Cheap gates** (`policies.py:pre_check`) — fewer than `INITIATIVE_TRIGGER_SIZE` messages in the window; the chat's newest message is the bot's own; the last bot message is inside `INITIATIVE_COOLDOWN_MINUTES`; fewer than `INITIATIVE_MIN_GAP_MESSAGES` user messages since it. The newest-message check reads `get_last_message(chat_id)` rather than `messages[-1]` — the window is fetched before the check runs, so a message can land in between (the bot's own reply included), and this guard has to see what was actually said last, not what the window happened to end on.
4. **Evaluation** (`processors.py:evaluate_initiative`) — one LLM call, model `initiative/v1`, prompt `initiative/v1`, `with_structured_output(InitiativeDecision)`. The window renders as one flat numbered list (`#N ▸ {ai_format}`) with the bot's own turns included **in `ai_format`, not `response_format`** — the latter strips the nickname, and in a flat list nothing else says whose line is whose. The model returns `score`, `reason`, and a 1-based `target_index` (or null for "to the chat as a whole"). Everything that can go wrong — a raise, an empty response — returns `score=0` with a `reason` string; nothing propagates.
5. **Decision** (`policies.py:decide`) — `score >= INITIATIVE_SCORE_THRESHOLD`, with out-of-range scores refused.
6. **Reply** (`_run_initiative_reply`) — dispatched with `asyncio.create_task`: typing action, a `Replier` targeted at the chosen message, a fresh `LAST_MESSAGES_SIZE` window, `character.respond`.

`InitiativeDecision.target_index` carries **no** pydantic bound, deliberately. `0` is the natural encoding of "no target" for a model shown a 1-based list, and a `gt=0` there raises inside `ainvoke` — which the broad except turns into `score=0, reason='Initiative evaluation error'`, indistinguishable in the log from the model choosing to stay quiet, and discarding a verdict whose window the watermark has already consumed. `processors.py` normalises `0`, negatives and out-of-range to `None` instead.

The evaluation window and the reply window are **different sizes**, and that is a live hazard rather than a detail: the judge reads `INITIATIVE_RUN_MESSAGES_MAX_SIZE` (50) and the character reads `LAST_MESSAGES_SIZE` (40), so a target picked from the older half of the judge's window is absent from the prompt the character answers — no `[TARGET]` marker, so the model takes v9's unmarked branch, while `Replier` still threads a Telegram quote to that invisible message. `_with_target` closes it by prepending a target missing from the reply window, which is chronologically correct because such a target is older than everything in that window by construction.

The watermark lives per chat in `mongo.initiative_runs` (`repository.py`), `last_message_time` set to the newest message the claim took. `_get_messages` reads the **newest** `INITIATIVE_RUN_MESSAGES_MAX_SIZE` messages past it (`sort_order=-1`), so a backlog past the cap is dropped — deliberately the opposite of the memory and embedding intake: a moment that has passed is not worth answering, and the oldest-first read this replaced made the first claim after a cooldown judge the conversation from an hour earlier. It advances when `pre_check` passes, **not** when the bot decides to speak: what is being rate-limited is the evaluation call, and re-reading a window the model already declined buys the same verdict twice. With no prior run the same query runs with no lower bound, so a chat with history opens on its newest messages rather than judging a year-old conversation.

`character.memory` is deliberately **not** re-stamped inside `_run_initiative_reply`. `characters/repository.py:get_character` hands out a module-level singleton, so a detached task writing to `.memory` can land this chat's snapshot in another chat's in-flight reply; the snapshot is passed into `get_chat_character` up in `run_initiative_checks` instead. The read direction of that race is pre-existing and unfixed — any concurrent reply can observe a `.memory` some other chat stamped — and closing it means a per-call copy of `Character`, not a smaller edit here.

`MemoryData.initiative_format()` (`memory/models.py`) is a second, smaller rendering of a snapshot for this prompt: participant traits and running jokes only — no `recent`, no topics, no ages. The judge needs to know who these people are, not what they said on Tuesday.

Known gap: nothing ties `INITIATIVE_RUN_MESSAGES_MAX_SIZE` to `INITIATIVE_TRIGGER_SIZE` the way `_fetch_caps_exceed_triggers` ties the memory and embedding pairs. Set the trigger above the cap — both are configmap-exposed repo vars — and `pre_check` can never pass, silently and forever.
