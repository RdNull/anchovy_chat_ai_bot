# Initiative pipeline detail

Loaded automatically when Claude reads a file under `src/initiative/`. Companion to the root `CLAUDE.md`; read that first for the message flow and cross-cutting settings.

**Initiative** (`src/initiative/`): the bot deciding, unprompted, that a conversation is worth a line — a separate scoring call behind deterministic gates. Ships as a dry run (`INITIATIVE_ENABLED=False`). See **Initiative pipeline** below.

### Initiative pipeline (`src/initiative/`)

An unprompted reply — the bot deciding a conversation it was not addressed in is worth a line. It replaces `RANDOM_REPLY_CHANCE`/`RANDOM_REPLY_COOLDOWN_MINUTES`, which fired on a coin flip with no idea what it was interrupting.

`handlers.py:run_initiative_checks` is the first stage of `run_followups` (`src/messages/followups.py`), so it is evaluated after every message. In order:

1. **Kill switch** — `settings.INITIATIVE_CHECKS_ENABLED` off returns before any DB read. It is one of *two* flags: `INITIATIVE_ENABLED` gates only the final send, so the pipeline can run as a dry run — evaluated, scored and logged, nothing sent. That is how it ships (`INITIATIVE_CHECKS_ENABLED=True`, `INITIATIVE_ENABLED=False`), and it is what calibrates the threshold against real conversations.
2. **Claim** (`_claim_window`) — first the in-flight check (below), then read the watermark, build and cut the window (`_get_messages` + `_split_window`), run `pre_check` on the resulting candidates, advance the watermark and set the in-flight marker, all inside `INITIATIVE_RUN_LOCK`. The lock is module-level and shared by every chat, like `memory.handlers.MEMORY_UPDATE_LOCK`, but the critical section ends *before* the LLM call. It is what makes the read-then-write atomic: `run_followups` is a detached task per message, so two messages arriving together would otherwise both read the same watermark, claim the same window and answer it twice.
3. **Cheap gates** (`policies.py:pre_check`) — fewer than `INITIATIVE_TRIGGER_SIZE` messages **among the candidates** (context does not count) — counted after `collapse_repeats`, so a burst of identical messages from one author is one message (`messages_too_few` reports `count` = groups and `raw_count` = messages); the chat's newest message is the bot's own; the last bot message is inside `INITIATIVE_COOLDOWN_MINUTES`; fewer than `INITIATIVE_MIN_GAP_MESSAGES` user messages since it; the chat has already sent `INITIATIVE_DAILY_LIMIT` initiative replies in the rolling 24h before now. The newest-message check reads `get_last_message(chat_id)` rather than `messages[-1]` — the window is fetched before the check runs, so a message can land in between (the bot's own reply included), and this guard has to see what was actually said last, not what the window happened to end on. The daily-limit gate is last, after the other four, so their skip-reason counts in Axiom stay comparable across the change; it runs before the claim, so a capped chat costs no LLM call and does not advance the watermark, same as the gates above it.
4. **Evaluation** (`processors.py:evaluate_initiative`) — one LLM call, model `initiative/v1`, prompt `initiative/v1`, `with_structured_output(InitiativeDecision)`. The prompt renders two blocks: context lines unnumbered (`▸ {ai_format_for(character.nickname)}`), candidates numbered (`#N ▸ …`) — the bot's own turns included **in the `ai_format` family, not `response_format`**, with `bot_nickname` the answering character's tagged nickname so the reactions line names its own reactions — the latter strips the nickname, and nothing else in the list says whose line is whose. An empty context list drops the block and its `РАНЕЕ В РАЗГОВОРЕ` label entirely rather than rendering an empty heading. The model returns `score`, `reason`, and a 1-based `target_index` into the candidates only (or null for "to the chat as a whole") — the context block is structurally unnumbered, so the model has no valid index to give one. Everything that can go wrong — a raise, an empty response — returns `score=0` with a `reason` string; nothing propagates.
5. **Decision** (`policies.py:decide`) — `score >= INITIATIVE_SCORE_THRESHOLD`, with out-of-range scores refused.
6. **Reply** (`_run_initiative_reply`) — dispatched with `asyncio.create_task` (held in `_REPLY_TASKS` so it cannot be garbage-collected mid-run): typing action, a `Replier` targeted at the chosen message, a fresh `LAST_MESSAGES_SIZE` window, `character.respond`. Afterwards, if `Replier.delivered` holds `ReplyKind.TEXT` or `ReplyKind.STICKER`, `mark_initiative_replied(run_id)` stamps the daily slot; a reaction alone or nothing at all spends none. The logged `outcome` is separate from the slot: anything delivered, a reaction included, is `delivered`.

The daily cap exists because the cooldown alone does not bound volume: once it expires, every new batch of candidates gets its own claim and its own shot at the judge, and the judge's scores cluster tightly around the threshold rather than trailing off — so a quiet chat sends rarely and a busy one sends roughly as often as the cooldown allows. `INITIATIVE_DAILY_LIMIT` (default 3) is the hard budget; the judge stays the quality filter on top of it, not the rate limiter.

`InitiativeDecision.target_index` carries **no** pydantic bound, deliberately. `0` is the natural encoding of "no target" for a model shown a 1-based list, and a `gt=0` there raises inside `ainvoke` — which the broad except turns into `score=0, reason='Initiative evaluation error'`, indistinguishable in the log from the model choosing to stay quiet, and discarding a verdict whose window the watermark has already consumed. `processors.py` normalises `0`, negatives and out-of-range to `None` instead — but a nonzero index that still fails to resolve (negative, or past the end of the candidates) additionally gets its own `logger.warning` line, so the dry run can tell "the model gave a bad index" apart from "the model said no target" (`0` or `null`, which log nothing extra).

The terminal `INITIATIVE_EVALUATE` line also carries `target_distance` (`len(candidates) - target_index`, `0` for the newest candidate) and `target_age_s` (seconds between the target's `created_at` and the newest candidate's), both omitted when there is no target. `target_index` alone counts from the candidates' *oldest* message, so it can't tell a stale target from a large window apart — these two answer that directly.

The evaluation window and the reply window are **different sizes**, and that is a live hazard rather than a detail: the judge's candidates read `INITIATIVE_RUN_MESSAGES_MAX_SIZE` (50) and the character reads `LAST_MESSAGES_SIZE` (40), so a target picked from the older half of the candidates is absent from the prompt the character answers — no `[TARGET]` marker, so the model takes v9's unmarked branch, while `Replier` still threads a Telegram quote to that invisible message. `_with_target` closes it by prepending a target missing from the reply window, which is chronologically correct because such a target is older than everything in that window by construction. A target can never be a context message — `target_index` only ever addresses the candidates — so this hazard is bounded by `INITIATIVE_RUN_MESSAGES_MAX_SIZE` alone, unaffected by `INITIATIVE_CONTEXT_SIZE`.

### In-flight guard, delivery-time slot, repeat collapsing

**In flight.** `_IN_FLIGHT: dict[int, float]` (chat_id → `time.monotonic()` at claim) allows one run per chat between claim and reply. The gates read *saved* bot messages and the reply is saved seconds after the claim, so without it a burst claimed every few messages (16 stickers in 3 s once dispatched twice). `_claim_window` checks it first, under the lock: a live marker logs `INITIATIVE_SKIPPED reason='in_flight' age_s` and returns an empty claim without touching the watermark, so messages arriving mid-run stay candidates. The marker is set right after `pre_check` passes. Ownership: `run_initiative_checks` clears it in a `finally` on every non-dispatch exit (below threshold, dry run, any exception — logged as `INITIATIVE_RUN_ERROR`, never raised); on dispatch `_run_initiative_reply` owns it and clears it in its own `finally`, after the slot stamp, so the next claim never sees "not in flight" and "slot free" at once. A marker older than `_IN_FLIGHT_STALE_S` (`AI_TIMEOUT + 60`, module constant) is overwritten with an `INITIATIVE_IN_FLIGHT_STALE` warning; any hit means a clear path is missing. State is in-process — one replica, and a restart kills the task anyway. Gate order: `in_flight`, `messages_too_few`, `last_from_ai`, `cooldown`, `gap_too_small`, `daily_limit`.

**Slot at delivery.** `replied_at` (what `count_replied_since` counts) is written by the reply task, not at dispatch. `Replier.delivered` is an append-only list of kinds (`ReplyKind`: `text`, `sticker`, `reaction`), appended after the Telegram call succeeds. Timeout/error fallback texts go through `reply_message`, so they count.

**Events.** `INITIATIVE_DISPATCHED` (`score`, `run_id`) at the `create_task` site — it replaced `INITIATIVE_REPLY_SENT`; `INITIATIVE_REPLY_DONE` once per reply task: `outcome` ∈ `delivered | empty | error` (`delivered` = at least one text, sticker or reaction went out and nothing raised; `empty` = nothing at all was delivered), `delivered_kinds`, `slot_spent` (text or sticker only, so a reaction-only run logs `delivered` with `slot_spent=false`), `elapsed_ms`. `INITIATIVE_CLAIMED` also carries `candidate_groups`.

**Repeat collapsing.** `policies.py:collapse_repeats` merges consecutive messages with the same author (`nickname`, `role`) and the same content key (stripped text, media `unique_id`); a message with neither never merges; the representative is the run's last message. `pre_check` counts groups, and `evaluate_initiative` renders one `#N` line per group with a ` ×count` suffix when count > 1. `target_index` addresses groups (`groups[N-1].representative`), and `target_distance` is in groups. The claim, watermark and `INITIATIVE_WINDOW` still count raw messages. The judge prompt has no legend for `×N` yet.

### Window construction (`_get_messages` / `_split_window` / `_claim_window`)

The watermark lives per chat in `mongo.initiative_runs` (`repository.py`), `last_message_time` set to the newest **candidate** the claim took. Each run document also carries an optional `replied_at`, stamped by `mark_initiative_replied` from `_run_initiative_reply` once text or a sticker was actually delivered — which is what `count_replied_since(chat_id, window)` counts against `INITIATIVE_DAILY_LIMIT`. The 24h window is `pre_check`'s to choose (`policies.py:_DAILY_LIMIT_WINDOW`), not baked into the repository function — `count_replied_since` is otherwise a plain rolling-window count, reusable for any window a future caller wants. Dry-run, below-threshold and empty runs never stamp it. `save_initiative_run` returns the new document's id so the send path can address the exact run it claimed — `_claim_window` hands both the id and the two message lists back as one `ClaimedWindow` dataclass (`context`, `candidates`, `run_id`), rather than a bare tuple, since three positional return values stopped being self-explanatory at the call site. There is no index on `(chat_id, replied_at)` — `initiative_runs` is unindexed today like every other collection in this project, and at one row per claim per chat the unindexed scan `get_last_initiative_run` already does on every message costs more than this count does. `_get_messages(chat_id, watermark)` fetches two ranges, both through `fetch_last_messages` so pending media descriptions are awaited: the newest `INITIATIVE_RUN_MESSAGES_MAX_SIZE` messages strictly after the watermark (candidates), and — only when a watermark exists — the newest `INITIATIVE_CONTEXT_SIZE` messages at or before it (context, `to_date_inclusive=True` so the watermark message itself, the last thing the previous run judged, is included). `INITIATIVE_RUN_MESSAGES_MAX_SIZE` bounds the candidate half only; the total fetch is that plus `INITIATIVE_CONTEXT_SIZE`. Cold start (no watermark) skips the context fetch entirely — a chat with history opens on its newest messages, unpadded, rather than judging a year-old conversation. The two ranges cannot overlap, so `context + candidates` concatenates straight into one chronological sequence.

`_split_window` then runs `policies.py:split_at_gap` over that sequence and cuts it at the newest inter-message gap larger than `INITIATIVE_GAP_MINUTES` (strictly greater — a gap exactly at the threshold does not cut), keeping only the suffix after it. This is what stops a quiet chat from concatenating unrelated conversations into one judged window: a window that once spanned 13h46m across four separate threads is now cut down to the live one. The surviving suffix is then re-partitioned around the watermark into `context` (`created_at <= watermark`) and `candidates` (`created_at > watermark`, or everything when there is no watermark) — a cut can land inside either half. Cutting inside the candidate region can empty `context` entirely (correct: that's a fresh conversation with nothing worth carrying forward); cutting inside the context region only trims it. One `INITIATIVE_WINDOW` event — `fetched`, `cut_gap_minutes` (a real `None`, not the string `"none"`, when the window was not cut), `context_count`, `candidate_count` (`chat_id` comes from the bound log context, not a field on the event) — is emitted here, **before** `pre_check` runs, so a quiet chat blocked on gate 1 is distinguishable in the logs from a live chat having its thread chopped.

Messages the cut drops are **not** queued or deferred — same rule as the plain backlog cap below: a moment that has passed is not worth answering. They can still resurface as read-only context on a later run, once the watermark has moved past them.

`_claim_window` runs the split *before* `pre_check`, so `INITIATIVE_TRIGGER_SIZE` now means "messages in one live conversation," not "messages accumulated since the last judgment" — a window that scored "too early, wait" is no longer permanently lost, since the watermark only advances past a candidate run that actually clears `pre_check`. A backlog past `INITIATIVE_RUN_MESSAGES_MAX_SIZE` is still dropped, not deferred, deliberately the opposite of the memory and embedding intake: the oldest-first read this replaced made the first claim after a cooldown judge the conversation from an hour earlier. The watermark advances when `pre_check` passes, **not** when the bot decides to speak: what is being rate-limited is the evaluation call, and re-reading a window the model already declined buys the same verdict twice.

`character.memory` is deliberately **not** re-stamped inside `_run_initiative_reply`. `characters/registry.py:get_character` hands out a module-level singleton, so a detached task writing to `.memory` can land this chat's snapshot in another chat's in-flight reply; the snapshot is passed into `get_chat_character` up in `run_initiative_checks` instead. The read direction of that race is pre-existing and unfixed — any concurrent reply can observe a `.memory` some other chat stamped — and closing it means a per-call copy of `Character`, not a smaller edit here.

`MemoryData.initiative_format()` (`memory/models.py`) is a second, smaller rendering of a snapshot for this prompt: participant traits and running jokes only — no `recent`, no topics, no ages. The judge needs to know who these people are, not what they said on Tuesday.
