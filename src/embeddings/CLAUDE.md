# Embeddings, RAG and sticker replies detail

Loaded automatically when Claude reads a file under `src/embeddings/`. Companion to the root `CLAUDE.md`; read that first for the message flow and cross-cutting settings.

**Embeddings/RAG** (`src/embeddings/client.py` + `src/processors/context/embeddings.py`): Messages are chunked (window=8, overlap=3), assigned UUID chunk IDs, and stored in Qdrant. An `AsyncCache` on the embeddings client avoids re-embedding identical text. LLM tool `search_messages` performs semantic search with cosine similarity.

**Sticker replies** (`src/embeddings/stickers.py`, `find_stickers`/`send_sticker`): the group's own stickers, made findable. Everything a sticker needs was already collected — the media pipeline downloads, hashes, deduplicates and vision-describes every one — but nothing read it back.

*Identity.* `messages/parsing.py:_mark_sticker` stamps `type=STICKER` and `sticker_emoji` onto freshly parsed media from the PTB object — an `isinstance` narrowing at the call site, leaving `_get_message_medium`'s signature alone. That is the only place the system can learn it: the extension cannot tell, and on first sighting there is no row to read. `get_message_media_data` therefore reads **only** the description row, with the sticker fields defaulting to `None`; the live parse overlays afterwards and so wins over a row written before stickers were typed, which is what lets the pipeline backfill it. `_parse_media_description` reads `sticker_emoji` with `data.get`, unlike its siblings, because every row written before this unit lacks the key.

*The two `media_id`s.* **`messages.media_id` holds a `file_id` and can be sent with; `media_descriptions.media_id` holds a `file_unique_id` and cannot.** The index is built over the latter, so it holds identity only, and `get_sendable_file_id` resolves identity to a sendable id at send time by reading the newest carrier message — a re-issued `file_id` then wins without a reindex. The field was deliberately not renamed (an `updateMany $rename` racing a k8s rollout is not worth a cosmetic fix); the docstring and this line are the mitigation.

*Index.* `StickerEmbeddingsClient` (collection `stickers`) embeds `emoji | description | ocr_text`, emoji first so a free human-authored sentiment label is not averaged into a long description. `_point_id` derives the point id from `unique_id` via md5 — the `chunk_messages` trick — so a re-run upserts; `facts.py` uses `uuid4()` there and duplicates on every backfill. Only `status == READY` rows are indexed, and `get_sticker` re-checks status when it reads the row back. There is no `chat_id` filter: `media_descriptions` has no `chat_id` and the corpus is global by construction, so the per-chat concern is recency and that is enforced against `messages` in the tool. `search_sticker_ids` passes no filter kwargs, so `_search` builds `Filter(must=[])` — verified against Qdrant to be accepted and to return `[]` on an empty collection, which is why `_search` needed no change. `_get_description` imports the media repository inside the function: `src/messages/media/__init__.py` eagerly imports `pipeline`, which imports this module, so a module-level import makes the cycle bite whenever `src.embeddings.stickers` is imported first — as `src/scripts/create_sticker_embeddings.py` does.

*How the corpus fills.* Two hooks, both in `handle_media_message`, and neither gated on `ENABLE_STICKER_REPLIES` — the flag gates the tools, and the corpus must accumulate while it is off. A sticker seen for the first time is typed at creation and indexed at the end of the function once its description lands. A sticker whose row **predates** this unit is typed `image` and already READY, and `handle_media_message` returns early on any READY description — so `_backfill_sticker` runs *before* both early returns, retypes it and indexes it. That placement is the point: without it the corpus could only ever grow from stickers nobody in the group had ever sent, which is far too slow to be useful, and `create_sticker_embeddings.py` would match nothing. Re-sighting a known sticker is the common case, so ordinary traffic does the backfill; there is no migration and the script is only the re-index path after an embedding-model change. For that to hold, `handlers.py:handle_conversation` dispatches the pipeline for **any** media rather than only `PENDING` media — gating on status there would leave the backfill unreachable on the path most stickers actually arrive by, since a known sticker reads back READY. The backfill costs one `find_one` per media message, because the status short-circuit can no longer skip the fetch.

*Retrieval.* `find_stickers` returns candidates and the character picks, rather than sending the top hit: nearest-neighbour returns the most literally relevant sticker, which is frequently the least funny one, so the character is the filter and retrieval only has to be roughly right. `STICKER_SCORE_THRESHOLD` is `0.25`, looser than `facts.py`'s `0.6`, for the same reason. The «пустой список» line in its description is load-bearing: under a cold start an empty list is the common case, and a model that reads it as "retry" burns one of three context-tool calls.

*The query is a picture, not a reply.* The tool takes `queries: list[str] | str` — 1–3 short descriptions of an **image**, clamped at `_MAX_QUERIES` with a warn-and-truncate, deduplicated, and probed one at a time. Both halves of that signature are corrections to observed behaviour. Given one free-form string the model wrote «ок босс или ладно или похуй или клоун» — the replies it was weighing, not anything the corpus is described as — so the description now says what is actually being matched (the emoji + vision description + OCR text `sticker_embedding_text` builds) and what a query looks like; that is the half that fixes the bug, and no amount of fusion substitutes for it. Given one slot it also packed four concepts into it, which is what the list is for. The `| str` is not decoration: `@tool` infers the args schema from the hint and pydantic validates *before* the body, so a bare string against a bare `list[str]` raises inside `ToolRegistry.execute` — a context tool, so the loop's `ToolFailure` recovery does not cover it — and unwinds to `respond`'s broad except, costing the whole turn. Splitting a string on «или» was considered and rejected: on the two real calls it turns the bad one into four bad searches and fragments the good one into one useful probe plus a junk probe carrying equal weight.

*Fusion.* Probes are merged by **Reciprocal Rank Fusion** (`_fuse`, `k=60`), never by score. Cosine scores from different query embeddings are not calibrated against each other, so a concatenate-and-sort merge is a single-probe result with extra steps — one probe's scoring quirk dominates while the others silently contribute nothing, and the output looks fine either way. `StickerSearchResult` therefore carries **no** `score` field: removing it is what keeps that merge from being written back in. Ties resolve toward the earlier probe and the better rank (`dict` insertion order plus a stable `sorted`), which is what makes the fusion test assertable.

*Order of operations.* Probe → fuse → recency exclusion → hydrate-and-trim. `search_stickers` was split into `search_sticker_ids` (Qdrant only, no Mongo) and `get_sticker` (the Mongo read plus the `READY` re-check), because hydrating per hit would read the same row once per probe that returned it and once more for every candidate fusion then discards. Hydration walks the fused list in order and stops at `STICKER_SEARCH_LIMIT`, so it costs one read per candidate the character actually sees. The old `limit + len(excluded)` over-fetch is gone — trimming now happens after the exclusion, so a recent sticker no longer eats into the final count. Probes run **sequentially**, not gathered: `_search` calls `_check_collection` on the shared base client and concurrent creates race on a cold index; `elapsed_ms` in the log below is what would justify revisiting that.

Observability: one `TOOL_STICKER_SEARCH chat_id=… queries=… hits=… contrib=… fused=… returned=… elapsed_ms=…` line per call, `hits` and `contrib` joined positionally against `queries`. `hits` is what a probe returned; `contrib` is how many of the *returned* candidates it supplied. Without `contrib`, «did the second probe ever contribute anything» — the only question that says whether multi-query earned its place — is unanswerable.

*Sending.* `send_sticker` resolves the id, and on a missing carrier or a `telegram.error.BadRequest` drops the point from Qdrant and returns `ToolFailure('стикер недоступен')` so the loop can answer some other way. `BadRequest` specifically, not bare `Exception` — a network blip must surface as an error rather than quietly evicting a good sticker. `Replier.reply_sticker` persists the send: that is what the recency exclusion reads, and what puts the bot's own sticker into `ai_format` history.

Observability: one `STICKER_CORPUS size=… enabled=…` line at boot (`src/bot.py:log_sticker_corpus`), the only caller of `sticker_corpus_size()`. It is how a cold start is watched warming up; if the number stalls, that is the evidence the group recycles a very small sticker set — the one thing that would make the narrow-vocabulary decision worth revisiting.

The retrieval eval suite (`evals/stickers/`) is deliberately deferred: under a cold start there is no corpus to hand-label. When it is built, grade **recall-at-K**, not top-1 — what matters is whether a good option was among the candidates the character saw.
