# Structured logging detail

Loaded automatically when Claude reads a file matching the globs above. Companion to the root `CLAUDE.md`; the collector-side half of this (the `json_parser`/`filter/noise` operators) lives in `.claude/rules/deployment.md` instead, since it loads on `manifests/**`.

**`src/logs.py`** installs a `python-json-logger` `JsonFormatter` in place of `basicConfig`'s text format — one JSON object per line to stdout, so `kubectl logs` and Axiom show the same bytes and a `json_parser` operator in the collector can lift the keys into OTLP attributes. JSON formatting is unconditional — there is no environment-switched branch. The format string carries no `%(asctime)s`: the CRI envelope already stamps the record time and the collector puts it in `_time`, so a formatted timestamp was ~24 redundant bytes per event. `%(name)s` (renamed to `logger`) is what separates `httpx`/`telegram.ext`/`asyncio` from our own records — though since every module does `from src.logs import logger`, `record.name` is `'bot'` for all of our own call sites and only ever separates *us* from third-party loggers, not one call site from another. `rename_fields` maps `message` → `msg` (the collector moves this back into `body`) and `exc_info` → `stack` (a traceback becomes one string on one event); `json_ensure_ascii=False` because the chat is Russian and escaping Cyrillic to `\uXXXX` triples the byte size of any line carrying chat text; `json_default=repr` so a stray `ObjectId`, `datetime` or pydantic model in an `extra` never raises inside logging itself.

`RedactBotToken` and `TelegramPollingFilter` are untouched by any of this — same classes, same behaviour, same handler-attachment loop and its comment. `RedactBotToken` is attached to the handler (a filter on a logger never sees records propagated up from `httpx`); `TelegramPollingFilter`, unlike the root `CLAUDE.md`'s summary of it, is attached to the `httpx` **logger** specifically (`src/logs.py:98`), not to the handler — it only ever needs to see `httpx`'s own records, so it does not need the propagation reach `RedactBotToken` does.

**`src/log_context.py`** (new) carries the chat/request identity that the message text used to. Two ways to bind it onto a `ContextVar`, chosen per call site by whether that site can fire more than once inside one long-lived task:

- `log_context(**fields)`, a context manager: sets a *new* dict over the current one and resets to the prior value on exit, so nested calls shadow without mutating the outer binding and concurrent tasks sharing an ancestor never see each other's nested fields.
- `push_log_context(**fields)`: the same merge, no `with`, no reset — it leans on the fact that `asyncio.create_task` copies the *current* context into a new task, so a task spawned once and left to finish needs nothing to clean up after it.

Both auto-generate `request_id` (`uuid4().hex[:8]`) the first time one is needed in a chain — a call whose current context and own `fields` both lack `request_id` mints one; every nested or subsequent call in the same context inherits it unchanged. This is why almost no call site passes `request_id=` explicitly any more.

**Which one to use is not a style choice — it was checked against both libraries' actual dispatch code before deciding, because guessing wrong means a silent, permanent bug.** `python-telegram-bot`'s default update loop (`max_concurrent_updates=1`, the default) and this project's `scheduler` package both run *one persistent task* that loops over many logical firings — PTB's `__update_fetcher` does `while True: await self.__process_update_wrapper(update)`; `scheduler`'s `__supervise_job` does `while ...: await job._exec(...)` — neither spawns a task per update or per firing. A `push_log_context` at either site would bind `request_id` on the very first firing and never regenerate it, since the auto-generation only fires when one is absent: every update or scheduled run for the rest of the process's life would carry the same stale id. `uvicorn`, by contrast, really does call `loop.create_task(cycle.run_asgi(app))` per HTTP request, not per connection, so a keep-alive connection's next request already gets an isolated task and a fresh context copy.

That split is why:
- `ContextBindingApplication` (`src/bot.py`), a one-method `Application` subclass overriding `process_update` to bind `chat_id`/`user_id`, and `tasks/facts.py`/`tasks/memory.py` (bind `task=`) all use `log_context` — each is the one-persistent-task case.
- `log_sticker_corpus` (a dedicated task at boot, never fired again), `BearerAuth.__call__` (`src/blackbox/app.py`, bound once per HTTP request so a `BLACKBOX_HTTP` line and any `BLACKBOX_TOOL` line it triggers share one `request_id`), and both `scripts/create_*_embeddings.py` backfills (one CLI process, `asyncio.run`'s own fresh task) use `push_log_context` instead.

`ContextBindingApplication` is wired in via `ApplicationBuilder().application_class(ContextBindingApplication)` in `src/bot.py:main`. Binding here — rather than per-handler, as an earlier version of this did inside the `restricted` decorator — is what makes it reach *every* handler group's callback and the registered error handler alike: PTB dispatches each group either by awaiting the callback directly or via `self.create_task(...)` for the (default) non-blocking case, and routes a handler's exception to `add_error_handler`'s callback from within that same `process_update` call, so `create_task`'s context-copying carries the binding into both paths for free. `restricted` (`src/messages/utils.py`) no longer binds anything itself, including on its own rejection path (`ACCESS_DENIED`), which used to be the one place `chat_id`/`user_id` were passed explicitly because it *was* the binding site — it isn't any more. `error_handler` (`src/messages/handlers.py`) keeps its own defensive `log_context(chat_id=..., user_id=...)` rebind: PTB can call it for a failure with no associated update at all (a polling-level error), which never goes through `process_update` and so never bound anything upstream. The rebind is a no-op in the common case (an existing value is left alone) and the fallback in the uncommon one.

**`event(name, **fields)`** builds the `extra=` payload for a structured line: `logger.info('Memory updated', extra=event('MEMORY_EXTRACT', outcome='ok'))`. `logger` stays the stdlib logger, so `exc_info=`, `stacklevel=` and lazy `%s` args keep working untouched. Raises `ValueError` — at the call site, not inside logging — on:
- a key in `_RESERVED` (a `logging.LogRecord` attribute; passing one through `extra=` otherwise raises `Attempt to overwrite 'x' in LogRecord` at the call site anyway, just with a worse error)
- a key in `_COLLECTOR_OWNED` (`log`, `logtag` — owned by the collector's `container` operator; a collision would silently overwrite CRI metadata during the attributes merge)
- a name not matching `[a-z][a-z0-9_]*`

This is deliberately the one place a silent Axiom-side corruption can be introduced, so it fails loudly instead. `elapsed_ms(started)` (`round((time.monotonic() - started) * 1000)`) is the one helper every timed event uses, rather than restating `(time.monotonic() - started) * 1000` at each of the ~15 call sites that need it.

**The conversion.** All 141 `logger.*` call sites in `src/` (plus 3 in `scripts/dns_sync.py`) were converted from an interpolated message to a constant message plus `extra=event(...)`, following a fixed rule set: the message becomes a constant (`summarize count() by body` groups instead of fragmenting); every line gets a `SCREAMING_SNAKE` `<DOMAIN>_<ACTION>[_<OUTCOME>]` event name; `chat_id`/`user_id`/`request_id` come from the bound context and are never re-added as fields; field names are shared across subsystems (`count`, `outcome`, `elapsed_ms`, `reason`, `nick`, `tool`, …) rather than inventing a synonym per call site; types survive (`count=len(x)` not `str(len(x))`, `None` not `"none"`); no dynamic field names (`event('X', **{nick: value})` would mint one Axiom column per chat member); every multi-outcome operation gets a terminal event with `outcome=` from a closed vocabulary (`ok | empty | skipped | disabled | timeout | rate_limited | error | not_found`); and no chat text, tool arguments, LLM output or reply bodies at INFO — moved to a DEBUG companion line (`TOOL_CALL_ARGS`, `REPLY_TEXT`, `MEDIA_DESCRIBE_TEXT`, `MEMORY_EXTRACT_CONTENT`, …) — except four deliberate exceptions kept as-is because each is the subject of a standing investigation: `MEMORY_CHURN_LOST.text`, `MEMORY_DECAY.text`, `MEMORY_ATTRIBUTION_CONFLICT.text`, `TOOL_WEB_SEARCH.query`. Thirteen event names that already existed before this conversion keep those exact names — `MEMORY_CHURN`, `MEMORY_CHURN_LOST`, `MEMORY_DECAY`, `MEMORY_ATTRIBUTION_CONFLICT`, `MEMORY_TRAIT_OVERFLOW`, `TOOL_WEB_SEARCH`, `TOOL_STICKER_SEARCH`, `INITIATIVE_WINDOW`, `STICKER_CORPUS`, `BLACKBOX_TOOL`, `BLACKBOX_NOT_READY`, `BLACKBOX_HTTP`, `DNS_SYNC_FAILED` — they are cited by name in saved analysis.

**`LLM_MULTIPLE_TOOL_CALLS`** (`src/characters/character.py:_run_llm_loop`, renamed from
`LLM_MULTIPLE_DIRECT_TOOLS` — not one of the thirteen preserved names above, and the
event had never fired, so the rename cost nothing) fires whenever the model emits more
than one tool call in a single turn. It carries both `tool` (the direct tool that
answered — unchanged) and `tools` (every tool name in the batch, in call order,
`tools=[tc['name'] for tc in response.tool_calls]`) — the first list-valued INFO/WARNING
field alongside `TOOL_CALL.tool_args`, and the same reasoning applies: tool *names* are
metadata, not chat text or argument values, so the INFO/WARNING ban on the latter does not
reach them. `tools` is what lets a query tell "a context tool ran for nothing because a
direct tool in the same batch already answered" (e.g. `find_stickers` + `answer_text`)
apart from two direct tools racing (`answer_text` + `set_reaction`) — `tool` alone could
not distinguish them.

**`scripts/dns_sync.py`** carries its own four-line `JsonFormatter` setup, duplicated on purpose from `src/logs.py` rather than imported: the module's own contract is that it imports nothing from `src` (see its docstring), so it cannot share the helper that builds this for the bot. Its three events (`DNS_SYNC_OK`, `DNS_SYNC_SKIPPED`, `DNS_SYNC_FAILED`) carry `record`/`ip`/`outcome` fields built inline rather than through `event()`, for the same reason — no `src` import to reach the validator with.

**No `defaults={'event': 'UNSET'}` any more.** During the migration the formatter carried that default so an unconverted call site was findable (`attributes.event == 'UNSET'`) instead of producing a null column; it was removed once that query, scoped to `attributes.logger == 'bot'`, returned zero rows against the live dataset. Third-party records (`httpx`, `telegram.ext`, `asyncio`) that never pass their own `extra=` now simply have no `event` field, rather than carrying a placeholder.

**Tests.** `src/tests/test_logs.py` covers redaction (unchanged from before this migration) plus the `JsonFormatter`/`event()` contract: a formatted record parses as JSON with only the renamed standard keys; `event()` round-trips an int as an int, not a string; `event()` raises on a reserved key, a collector-owned key, and a malformed name; `exc_info=True` produces one record with a populated `stack` containing `Traceback (most recent call last)`; a non-serializable value (`ObjectId`) formats without raising; Cyrillic survives unescaped; and — the one interaction between the two changes that could silently regress a credential leak — `RedactBotToken` still redacts after the JSON pass, since the filter runs on the record and the formatter runs after it. `src/tests/test_log_context.py` covers both binding functions: `log_context` reaching a record inside its block and a task started within it, not reaching one started outside it or after the block exits, an explicit `extra=` beating the context value, nested calls shadowing without mutating the outer binding; `push_log_context` binding with no `with` block, never resetting what an earlier push in the same task bound, generating `request_id` once and keeping it across further pushes, and still reaching a task created afterward — each `push_log_context` test runs inside `asyncio.run(...)` rather than at a test function's own top level, since the whole point of the function is that it never resets, and calling it directly in a sync test body would leak into the interpreter's ambient context and bleed into later tests.
