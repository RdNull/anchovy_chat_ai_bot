# Deployment detail

Loaded automatically when Claude reads a file matching the globs above. Companion to the root `CLAUDE.md`.

**Deployment**: `Dockerfile` is a multi-stage build (builder venv + slim runtime, non-root `app` user). `.github/workflows/deploy.yml` builds/pushes the image to GHCR on push to `main`, then runs `deploy-k8s.sh`, which writes `bot-secrets`, applies `manifests/*.yaml` (bot Deployment, MongoDB and Qdrant StatefulSets, the ConfigMap, the mongo backup CronJob, the DNS sync CronJob) into the cluster's `default` namespace, and `manifests/blackbox/` into `blackbox` (both below), and waits on each rollout with `--timeout=5m` — the default is to block forever, which turns a wedged rollout into a CI job that hangs until GitHub's 6h limit. Both stores are waited on *before* the bot rolls, so it never starts against a store that is still coming up. The workflow holds a `concurrency: deploy-main` lock with `cancel-in-progress: false`, since two pushes in quick succession would otherwise run overlapping deploys against one cluster. Not relevant to local dev — use `docker compose up -d --build` instead.

`deploy-k8s.sh` renders those manifests through `envsubst`, which substitutes the **empty string** for any `${VAR}` the `deploy` job did not export. It never fails; it writes a blank. `MONGO_INITDB_ROOT_PASSWORD` was absent from that `env:` block from `9d0d110` (2026-06-14) until 2026-09-03, so every deploy overwrote `bot-secrets` with an empty mongo password — invisibly, because `secretKeyRef` values resolve at *container* creation and the running pod held the good one in memory across every subsequent `kubectl apply`. A node restart recreated the pod, it read the blanked secret, and the entrypoint refused to start with `both must be specified for a user to be created`. That message is itself the diagnosis: key-present-but-empty, where a *missing* key gives `CreateContainerConfigError`. The stored data was never at risk — on an initialized `dbPath` the injected password only satisfies that guard and puts `--auth` on the argv, while the credential that authenticates lives in `/data/db`.

Two things close the class instead of the instance. `src/tests/test_deploy_config.py` asserts that every `${VAR}` in `manifests/*.yaml` is exported by `jobs.deploy.env` (`IMAGE_TAG` excepted, since the `Deploy k8s` step sets it in its own step-level `env:`), and holds the shell guard against that set in both directions: it may require nothing the job does not export, and it must cover every key rendered into a Secret. `required_vars` walks `manifests/` recursively, so `manifests/blackbox/` is covered. `secret_keys` reads each YAML document and takes placeholders from `kind: Secret` documents only, so `dns-sync.yaml`'s image tag does not count as a secret. `deploy-k8s.sh` runs `set -euo pipefail` and refuses to deploy with any required variable empty, deliberately without `set -x`, which would print those secrets into the CI log. The configmap half is the quieter failure: `env_ignore_empty=True` in `src/settings.py` means a blanked value falls through to a code default, so the bot would run on defaults with nothing in the logs at all.

The Secret manifests (`manifests/secrets.yaml`, `manifests/blackbox/secrets.yaml`, the Secret in `manifests/dns-sync.yaml`) are the source of truth for which secret keys exist — every kube object stays under `manifests/`, and the script does not grow a line per secret. The cost is that secret values round-trip through a double-quoted YAML scalar, which `envsubst` cannot escape. Measured, rather than assumed: a `$` in a value is **safe**, since `envsubst` makes a single pass and never re-scans what it substituted; a `"` or a stray `\` is a parse error, so the deploy fails loudly; but `\t`-style escapes and literal newlines are *decoded by the YAML parser* and stored silently wrong. The manifest header carries that table, because the person who needs it is the one adding a secret. Two known consequences are accepted rather than fixed: that silent-corruption window, and `kubectl apply` retaining the rendered manifest — plaintext values included — in the object's `kubectl.kubernetes.io/last-applied-configuration` annotation. `kubectl apply --server-side` would remove the second, but server-side apply interacts badly with write-only `stringData` and was not adopted unverified.

The manifests hold four decisions that are easy to undo by accident. **Image tags are pinned** to what the cluster is actually running (`mongo:8.3.8`, `qdrant/qdrant:v1.19.0`, read off the pods and digest-matched against the published tags): `:latest` implies `imagePullPolicy: Always`, so every pod recreation is a chance to pull a new major over an existing volume — harmless until it isn't, exactly the shape of the secret bug above. **The bot Deployment is `strategy: Recreate` with `replicas: 1`**, both load-bearing rather than frugal: Telegram permits one `getUpdates` caller per token, and the default RollingUpdate's 25% `maxSurge` starts the new pod before the old one terminates, so every deploy ran two pollers for the length of the overlap. Whether that surfaces is a race, which is why it went unnoticed for so long: one pre-change pod's log carries 29 `Conflict: terminated by other getUpdates request` lines and the next carries none. **Every container declares `requests` and no `limits`**: requests buy Burstable QoS, and a BestEffort pod is the first thing kubelet evicts under node pressure, while a memory *limit* on mongo is actively harmful, since WiredTiger sizes its cache from the cgroup limit and any limit tight enough to matter on a 2Gi node OOM-kills mongod. **Probes are `tcpSocket` on mongo and `httpGet /readyz` + `/livez` on qdrant, and absent on the bot**: `mongosh --eval` is a full Node.js runtime and this node has one CPU, so a periodic exec probe costs more than the extra signal; the bot serves no health endpoint, and a polling loop that dies takes the process with it, so a probe would only restate the container's exit status. The two store probes are what make `rollout status statefulset/…` mean *serving* rather than *started*.

**The public edge** is cluster infrastructure installed once by `scripts/cluster-bootstrap.sh`, not by CI: Traefik (namespace `traefik`) and cert-manager (namespace `cert-manager`) by Helm at the chart versions pinned in the script, with values in `manifests/cluster/`, plus the `letsencrypt-staging` / `letsencrypt-prod` ClusterIssuers. Traefik is a DaemonSet on `hostPort` 80/443 (Calico's CNI config carries `portmap`) behind a `ClusterIP` Service, because a `LoadBalancer` Service makes the Linode CCM provision a billed NodeBalancer — the script fails if one exists. Its `updateStrategy` is `maxSurge: 0`, since a hostPort cannot surge. The dashboard is disabled outright (`api.dashboard: false`), and the chart's schema is strict, so a mistyped key fails the install. Traefik routes and cert-manager issues: Traefik's own ACME resolver persists to an `acme.json` that needs a volume, and a lost volume re-issues until Let's Encrypt rate-limits the domain. Traefik has its own namespace because its ServiceAccount reads Secrets cluster-wide. ingress-nginx was the original plan and was dropped because upstream stopped maintaining it in March 2026. The ClusterIssuers' HTTP-01 solver sets `ingressClassName: traefik`, and it is load-bearing: without it the solver's challenge Ingress goes unclaimed and the certificate never issues.

**Blackbox in the cluster** is `manifests/blackbox/`, namespace `blackbox`, applied by `deploy-k8s.sh` after the bot: `namespace.yaml` first, then every file through `envsubst | kubectl apply -n blackbox`, then `rollout status deployment/blackbox`. Every object also names its namespace. The pod runs the bot image with `command: python -m src.blackbox`, so `mcp` is now in `requirements.txt`. The namespace is the isolation boundary: Secrets cannot be mounted across namespaces, so this internet-facing pod holds only `blackbox-secrets` — `BLACKBOX_MCP_ACCESS_TOKEN`, `DATABASE_URL` from `${BLACKBOX_DATABASE_URL}` (the read-only user), and `OPENROUTER_API_KEY` from `${BLACKBOX_OPENROUTER_API_KEY}` (a separate low-cap key for query embeddings). `TELEGRAM_TOKEN` is the literal `unused-by-blackbox` in the Deployment env, because `_Settings` requires it. Stores are addressed cross-namespace (`qdrant.default.svc.cluster.local`, and the Mongo host inside the URI); the bot's short names are untouched. The pod settings:
- `automountServiceAccountToken: false`.
- `enableServiceLinks: false`. The kubelet injects Docker-links env vars for every Service in the namespace, and the `blackbox` Service's `BLACKBOX_PORT=tcp://<ip>:80` shadowed the setting of that name — the first rollout crashed at settings validation. `test_deploy_config.py:test_no_injected_service_variable_shadows_a_setting` computes the injected names for every pod running `${IMAGE_TAG}` and fails on any overlap with `_Settings` fields, so naming a Service after a settings prefix is caught in CI.
- `maxSurge: 0`, because a surge pod does not fit the node's ~390Mi memory headroom.
- Liveness is `/healthz`, readiness `/readyz`. Readiness pings both stores, so a bad RO URI or a NetworkPolicy that blocks them fails the CI rollout instead of the first tool call.

The Ingress:
- `ingressClassName: traefik`, host `mcp.anchovy-bot.rdnull.im`, path `/` (Prefix).
- `router.entrypoints: websecure`, so the token is never accepted over plain HTTP. The solver Ingress still gets `:80`.
- Rate limit and body size are `traefik.io/v1alpha1` Middleware objects referenced by `router.middlewares` (`blackbox-rate-limit@kubernetescrd`). `nginx.ingress.kubernetes.io/*` annotations are silently ignored here.
- The issuer annotation is `letsencrypt-prod`. Switch it back to `letsencrypt-staging` while iterating on the Ingress, since production issuance is rate-limited.

`networkpolicy.yaml` selects `app: blackbox` only, not the namespace, because cert-manager's solver pods run there too. It allows:
- Ingress: TCP 8000, only from `app.kubernetes.io/name: traefik` pods in the `traefik` namespace.
- Egress:
  - kube-dns on UDP/TCP 53
  - `app: mongo` on 27017 and `app: qdrant` on 6333 in `default`
  - TCP 443 to `0.0.0.0/0` minus the three private ranges — the one deliberate hole, for OpenRouter, since plain NetworkPolicy cannot match a domain

A policy later added in `default` to restrict ingress to the stores must name the `blackbox` namespace.

**DNS sync** (`manifests/dns-sync.yaml`, `scripts/dns_sync.py`) runs as a CronJob in `default`, every 10 minutes, with `concurrencyPolicy: Forbid`. It keeps the `mcp.anchovy-bot` A record in the Linode zone `rdnull.im` on the node's public IP, which changes on a node recycle (not a reboot). Its ServiceAccount is bound to a **ClusterRole** with `get`/`list` on nodes, because nodes are cluster-scoped and a namespaced Role cannot grant them. It is a standalone script outside `src/`, importing nothing from the bot: its settings are its own `DnsSyncSettings`, not `src/settings.py`, whose required Telegram token and Mongo URL this job must not hold, and it configures its own logging. It runs from the bot image (`python scripts/dns_sync.py`) only because that image is already on the node. One run:
- Take the single Ready node, or fail: two Ready nodes happen mid-recycle, and a guess could pick the node being drained.
- Select the address with `type == 'ExternalIP'` *and* IPv4. The node lists `InternalIP` 192.168.x first and an IPv6 ExternalIP too, and a record pointed at the wrong one resolves and fails silently.
- Refuse a private address (`PRIVATE_NETWORKS`; the real IP 172.104.x is outside 172.16/12, so no `startswith` checks).
- `PUT` only `target`, only on a mismatch, only on the one A record matched by name. Linode's update verb is PUT, and nothing is ever deleted.
- Log one `DNS_SYNC record=… node_ip=… record_ip=… action=unchanged|updated|refused` line either way.

The Cloud Firewall is attached by hand and is not in the repo.

`volumeClaimTemplates` is immutable on an existing StatefulSet, so the `1Gi`/`2Gi` requests in the mongo and qdrant manifests cannot be corrected in place — `kubectl apply` rejects the edit outright. Both bound volumes are 10Gi regardless, Linode's minimum. `manifests/backup-mongo.yaml` adds a nightly `mongodump` CronJob (03:17 UTC, `concurrencyPolicy: Forbid`) writing gzipped archives to a second 10Gi PVC and pruning past 7 days. It authenticates with `DATABASE_URL`, not `MONGO_INITDB_ROOT_PASSWORD`, and the distinction is the same one the incident turned on: on an initialized `dbPath` the injected root password is decorative, while `DATABASE_URL` is the credential proven to work because the bot is authenticating with it right now. That the two can disagree at all is an open item — the mongo password lives in two independent GitHub secrets, nothing reconciles them, and they would first disagree visibly on a pod restart.
